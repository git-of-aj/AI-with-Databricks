## Solution:
Yes. The important thing is that Failed to fetch is probably not an error from your Azure Function code itself.

It is a browser-side error generated by the Azure Portal's JavaScript:

TypeError: Failed to fetch
at https://portal.azure.com/...


That distinction is extremely useful for debugging.

1. Think about what the Portal "Test & Run" is actually doing

Your mental model may be:

You
  ↓
Azure Portal
  ↓
Azure Function runtime
  ↓
Your function code


But there are actually several layers:

┌───────────────────────┐
│ Browser               │
│ portal.azure.com      │
└───────────┬───────────┘
            │
            │ HTTP request
            ▼
┌───────────────────────┐
│ Function App endpoint │
│ xxx.azurewebsites.net │
└───────────┬───────────┘
            │
            ▼
┌───────────────────────┐
│ Azure Functions host  │
└───────────┬───────────┘
            │
            ▼
┌───────────────────────┐
│ Your function code    │
└───────────────────────┘


The error you're showing suggests the failure may be occurring before the request reaches your function code.

Microsoft specifically notes that the Portal's Code + Test/Test & Run functionality requires direct network access to the Function App, and CORS/network restrictions can prevent the browser from reaching it.

Your particular error:

TypeError: Failed to fetch


makes Layer A my first suspect, rather than Layer C.

Network

Authentication / Function key

   X

5. But there's an important distinction: CORS vs networking

This is where Azure Functions troubleshooting gets confusing.

Suppose you have:

Function App
    |
    +-- Private Endpoint
    |
    +-- VNet
    |
    +-- Access Restrictions
    |
    +-- Public network access disabled


Your laptop may be able to access the Function because you're connected to:

VPN
  ↓
Corporate network
  ↓
VNet
  ↓
Private Endpoint
  ↓
Function


But Azure Portal Test/Run may not have the same network path.

You get:

Browser / Portal
       |
       X
       |
Private Function App


And the browser simply reports:

Failed to fetch


That's why "the Function works from my application" does not necessarily prove that Portal Test/Run should work.

Microsoft explicitly says that private endpoints and inbound access restrictions can prevent Portal Code + Test from reaching the running Function.

Suppose your HTTP trigger is:

Authorization level: Function


Then the endpoint isn't simply:

POST https://xxx.azurewebsites.net/api/MyFunction


It needs a Function/Host key.

Browser

10. A very useful experiment

Don't immediately modify your Function code.

Instead, take the Function URL from:

Code + Test → Get Function URL

Then test it outside the Portal.

For example:

curl -v "https://<function-app>.azurewebsites.net/api/<function>"


If it's a POST:

curl -v \
  -X POST \
  -H "Content-Type: application/json" \
  -d '{"test":"hello"}' \
  "https://<function-app>.azurewebsites.net/api/<function>"


If it requires a function key:

curl -v \
  "https://<function-app>.azurewebsites.net/api/<function>?code=<FUNCTION_KEY>"


The -v is important because it exposes the actual network conversation.

You want to know:

DNS succeeded?
TCP connection?
TLS handshake?
HTTP status?
Response headers?
Response body?


That is much more informative than:

Failed to fetch
